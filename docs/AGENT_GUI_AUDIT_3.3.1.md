# 3.3.1 GUI 操作审计

## 范围和现场

基线为本仓库 `07db61f`（3.2.0），新实现合并了上游 `9de3a3f`（3.3.0）。
测试设备：vivo V2419A，Android 16，OriginOS `PD2419B_A_16.1.12.38.W10`，KernelSU / LSPosed，无线 ADB。

读取已有会话后只保留统计，不把用户消息、屏幕正文、凭据或原始数据库提交到仓库。
2945 条消息记录中有 443 次 `observe_screen`、308 次 `wait`；失败分类包括
`STALE_CONTENT` 13 次、`INPUT_DISPATCH_UNCONFIRMED` 11 次、`NO_FOCUSED_EDITABLE` 8 次、
`DISPLAY_FRAME_PENDING` 7 次、`UI_NO_PROGRESS` 5 次。这些计数描述已保存的历史，不能据此计算整机成功率。

## 静态分析和实现

- 虚拟屏动作以前只返回输入派发结果，Loop 常另做 `wait → observe_screen`。现在点击、长按、滑动、滚动、输入、按键、启动应用和打开 URI 附带动作后的 `after`。
- Root 确认输入处理结束，不等于应用已把状态更新到无障碍缓存。动作后给 View 队列 80ms 的短暂处理时间，再刷新目标根节点的缓存子树并读取。该等待不占一个工具或模型回合。
- `after` 有新的 `observation_id` 和执行范围，可直接用于下一步。状态比较包含 `checked`、`selected`、焦点、可用性、提示和交互标志，避免只改变开关状态时被判断成没有进展。
- 无有效 UI 树的页面按需取一张新截图，`screen_changed=null` 表示节点比较不能确定结果。不会把「没有节点」伪装成「画面没变化」。
- 后续观察失败只报告需要重新观察，不把已派发的动作改写成未执行或自动重放；原有无进展、输入无响应、有界恢复和权限检查继续生效。
- 停止或模型失败保留虚拟显示。续聊重新取得运行租约，并要求在输入前获取本轮观察，旧节点和坐标不能直接沿用。

## 实机对比

独立测试应用提供一个计数按钮。两组各点击 6 次，每次核对计数确实增加一次：

| 测量 | 基线：tap → wait(200ms) → observe | 新实现：读取 tap.after |
| --- | ---: | ---: |
| 有效动作 | 6 | 6 |
| 后续工具调用 | 18 | 6 |
| 附带图片 | 0 | 0 |
| 工具累计耗时 | 4886ms | 3916ms |
| 每步耗时 | 784 / 820 / 856 / 796 / 840 / 790ms | 650 / 656 / 646 / 649 / 635 / 680ms |

该场景减少约 67% 的工具调用和 20% 的工具耗时。初始启动与初始观察不在表中，模型和网络耗时也不在表中；这是同机合成场景的单次配对测量，不是所有应用的速度保证。

额外实机回归：动作附带的新观察连续点击 6 次通过 30 项检查；开关仅状态变化、未点中目标、中文和 emoji 的替换/追加输入通过 20 项检查；Canvas 无 UI 树页面通过 12 项检查，确认一个动作只执行一次并返回一张截图和未知变化状态。停止、续聊与失败保留现场通过 14 项检查。

## 使用边界

有明确进展时继续使用 `after`，无需例行插入观察和固定长等待。异步网络页面尚未完成、节点过期、截图不足或输入结果不明确时仍应重新观察或等待实际条件；观察到变化本身不代表任务已成功。新实现不增加设备权限，也不绕过主屏回退或重启授权。
